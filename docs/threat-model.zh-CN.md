# 威胁模型

[English](threat-model.md) | **简体中文**

Palette 防什么、假设什么，以及它刻意不做什么。

## 信任

**永远不可信：**

* Agent 发来的任何东西——参数、坐标、文本、`request_id`，以及它关于自己权限的任何主张；
* 客户机操作系统及其中的每一个应用，包括试图攻击宿主机的客户机；
* 网页、文档，以及屏幕上任何可见文本；
* 未来的远程客户端。

**可信：**

* 运维编写的 profile、权限策略、本服务；
* 运维安装的 QEMU 构建，以及宿主操作系统。

屏幕内容是**数据**。屏幕上出现的一条指令，不是来自运维的指令，服务里没有任何一处会把它当成
指令对待。

## 调用方可以打开的边界

有三个 profile 开关，会把本该由 profile 钉住的材料交给调用方。它们在
`profiles/strict-example.toml` 里全部关闭、在 `profiles/default.toml` 里全部打开，而三者的后果
并不等价——第三个是另一类东西。

| 开关 | 授予什么 | 服务还能做什么 |
| --- | --- | --- |
| `allow_agent_images` | 调用方指定基础镜像，于是 QEMU 启动用的磁盘不再是 profile 钉住的那一个 | 对该文件的内容无能为力。可写层仍是每实例独立的、仍属于服务、仍会被重置丢弃——但客户机里可能是任何东西 |
| `allow_agent_iso` | 调用方从任意宿主路径挂载 CD-ROM 或额外磁盘 | 无。文件以只读打开，路径记入实例 manifest |
| `allow_agent_qemu_args` | 调用方追加原始 QEMU 参数 | **无。** `-chardev`、`-device`、`-blockdev` 能读写宿主任意文件；`-mon`、`-vnc`、`-chardev socket` 会加出第二条驱动客户机的通道，单写入者保证随之静默失效 |

`allow_agent_qemu_args` 打开后，**本文档里所有参数级控制都降级为提示**：加速器取决于调用方最后
追加的那一条，`-display none` 旁边可以并排出现一个 VNC server，而环境变量白名单所保护的，是一个
现在会执行任何被交代内容的进程。读不懂调用方意图的服务没法据此过滤；假装能——比如维护一张“危险
参数”黑名单——比直说更糟，因为第一个没人想到要列进去的参数就能绕过它。

服务仍保留了调用方拿不走的一点：经额外参数引入的 monitor 或显示通道会被识别出来，并写进计划说明
与日志，让被破坏的单写入者保证可见，而不是无声。

## 边界与强制手段

| 风险 | 控制手段 |
| --- | --- |
| Agent 借管理接口触达宿主机 | 没有 `qmp_execute`、没有 HMP、没有通用 monitor 透传。命令允许列表是经过审查的常量，未知命令在本地就被拒绝，根本不会发出去。但若 `allow_agent_qemu_args` 打开，调用方仍可触达 QEMU 自身的参数面——见上文 |
| 管理通道被别处访问 | QMP 跑在服务自己启动的子进程的私有管道上。没有 TCP 监听、没有 VNC、没有 SPICE、没有显示窗口——除非调用方自己加一个 |
| 读写宿主机文件 | 任何**受管**路径都不会由调用方提供：镜像、frame、日志与审计都从可信配置和生成的标识组合而成，再经词法与链接两重检查收敛到 `runtime_root`。调用方提供的镜像、CD-ROM 与 QEMU 参数是有意的例外，按构造就在该收敛范围之外 |
| 客户机攻击宿主机 | QEMU 以非提权身份运行，设备集最小化，无共享目录、无透传，环境变量走白名单。请保持更新；固定版本不是跳过安全补丁的理由。调用方提供的设备或 chardev 不在此列 |
| 通过共享通道泄漏数据 | Palette 不会配置 9p、virtiofs、SMB、双向剪贴板或宿主设备直通中的任何一项。调用方自己传对应参数是他的决定 |
| 触达宿主机或内网 | `restricted-lab` 把客户机关在 slirp 沙箱内，`offline` 则完全不附带网卡。`nat` 让客户机拥有与宿主同等的出站能力且没有出站策略；配置的 `hostfwd` 会从另一个方向打穿沙箱。受强制的白名单会被拒绝，而不是被近似实现 |
| 资源耗尽 | 动作队列有界、文本长度与输入预算有界、动作时长有界、图像尺寸与像素数有界、审计文件增长有界、QEMU 进程有宿主侧内存上限，调用方提供的参数数量与单条长度也有界 |
| 两个写入者争抢同一个桌面 | 每台 VM 一个动作队列、一个控制权代次、没有额外的可写输入路径。额外参数加出来的那一条会被记录，而不是被阻止 |
| 日志泄漏秘密 | 审计只记动作类型、长度、时序和结果。绝不记输入正文、绝不记启动参数、绝不记截图、绝不记宿主机路径——调用方提供的路径进实例 manifest，与实例同生共死 |
| 重置删错东西 | 删除要求存在 manifest，且路径解析后必须落在 `runtime_root` 之内；并拒绝跟随链接。调用方提供的文件永远不会成为删除对象 |
| 页面诱导 Agent 提权 | 权限来自可信 profile。没有任何工具能授予权限。调用方提供的**参数**是唯一一处请求能自行扩大自身触达面的地方——这也正是那个开关单独存在、且默认值如其所是的原因 |

## Palette 不防什么

* **已经以同一宿主用户身份运行的恶意进程。** 任何能读这个用户文件的东西，都能读运行目录，
  也能调用同一个 QEMU 可执行文件。更强的隔离需要独立的低权限服务账户和操作系统沙箱——那是合理
  的下一步，不是本 MVP 自称具备的能力。
* **多租户。** 一个服务、一个运维、同一时刻一台 VM。没有按租户的授权、配额或审计隔离。
* **真实恶意代码。** 客户机是一台虚拟机，不是一份证明。请把它当作遏制手段，而不是恶意代码沙箱。
* **截图保持私密。** 截图会送到客户端所配置的那个模型。不落盘不等于没人看过。请使用测试账号和
  不含敏感资料的模板，并假定屏幕上的一切都已经到达模型。
* **远程传输。** 本构建只提供 stdio。Streamable HTTP 需要 TLS、身份认证、按 VM 的授权、严格的
  `Origin`/`Host` 校验、消息限额、限流、会话过期与审计——而且 MCP session id 不是身份。
* **有保证的 exactly-once。** 去重是进程内、有界的。在发出输入与记录结果之间崩溃，会留下一个
  结果不明的动作；服务会报告 `unknown`，而不是重放它。
* **可以传 QEMU 参数的调用方。** `allow_agent_qemu_args` 一旦打开，宿主边界就交给调用方去守，
  本文档里所有参数级控制都降级为提示。这是本清单里唯一一项属于配置选择、而非设计局限的条目：
  把开关关掉，边界就回来了。
* **可以指定基础镜像的调用方。** 此时客户机就是那个文件里的内容。来自不可信来源的镜像，请按
  “直接运行它”来对待。
* **把工具注解当授权。** `readOnlyHint` 和 `destructiveHint` 帮助客户端呈现决策。它们不替代
  任何东西：每一次调用都在服务端检查。

## 服务确实给出的保证

* 输入绝不会被发送到请求所指之外的实例，也不会基于已被其他动作作废的 frame 发送。
* 超时、响应丢失或后续截图失败，**绝不**触发自动重放。回执会写 `unknown`，是否再试一次由调用方
  决定。
* 只有在服务真的确认过之后，释放才会被报告为已确认。通道已死时产出的是“无法确认”，绝不是一句
  成功声明。
* 清理只触及 manifest 中登记、并被限制在运行根目录内的对象。调用方提供的文件以只读打开，永远
  不会被删除。
* 宿主机材料的开关是一次授权一项。能指定镜像，不等于能传参数；每一次拒绝都会指明本该放行的那个
  开关。
* `system_reset` 永远不会被当作重置：干净重置替换可写层，并让基础镜像逐字节保持不变；基础镜像由
  调用方指定时，对这一份文件同样成立。
