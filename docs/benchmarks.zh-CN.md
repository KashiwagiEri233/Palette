# 基准测试

[English](benchmarks.md) | **简体中文**

往下读之前，先把两件事说清楚。

**这里什么都还没测过。** 下面的数字是计划里的目标，现在仍然是目标。本机没有安装 QEMU，因此
没有任何真实的采集、输入或启动耗时被记录，也不存在任何基准报告。

**替身不等于测量。** 本仓库里的测试替身（一个假 QEMU 进程、一个进程内 QMP 服务器）之所以快，
是因为它们完全没有做虚拟化、渲染或客户机调度。拿它们测出来的时间只能说明 Python 层的开销，
完全不能说明真实桌面是否达到某个延迟目标。任何报告都必须把它的每一行标注为 `mock`、`TCG` 或
`WHPX`。

## 怎么测

```bash
PALETTE_E2E=1 PALETTE_E2E_QEMU=... PALETTE_E2E_IMAGE=... uv run pytest tests/e2e -v
```

在固定宿主上——一台 VM、1280×800、2 vCPU、4 GiB、客户机内无重负载——每一项数据都要连同宿主
CPU、内存和磁盘一并记录。

## 目标（不是结果）

| 测量项 | 目标 |
| --- | --- |
| “发起请求 → MCP 图像结果就绪”，100 次稳定采集 | P95 ≤ 500 ms |
| “动作开始 → 动作后图像就绪”，普通单击，不含模型推理 | P95 ≤ 1 s |
| 冷启动，拆成：QMP 可达 / 首个有效显示缓冲区 / 桌面就绪 | 分别记录，不设单一目标 |

长文本有自己的限速，不与单击共用延迟预算：输入 256 个字符意味着数百条输入消息，假装不是这样
只会定下一个不可能完成的目标，然后再悄悄认输。

## 时间花在哪

目标没达成时，先分解，再考虑增加复杂度：

1. **图像字节与编码** —— Pillow 的 PNG 编码往往就是最大的一项开销。
2. **临时文件 I/O** —— `screendump` 先写磁盘；服务再读回来并删掉它。
3. **QMP 往返** —— 一次管道写入加一次 JSON 响应。
4. **客户机 settle** —— 输入与采集之间配置的那段延时。
5. **排队等待** —— 排在别的动作后面的时间。

如果总量始终达不到、而瓶颈在采集 I/O，计划的答案是换一个 VNC 采集后端，而不是换个更快的替身：
QMP 的整屏 dump 本就不是为高帧率设计的，而 VNC 维护的是一块持续更新的 framebuffer。输入仍然
留在 QMP 上，所以只有采集路径会变。

## 正确性测量

有些验收标准是物理性质的，没有有用的替身版本：

* 在夹具网格的四个角、中心以及至少 200 个点上的点击精度，误差 ≤ 原图 2 像素；
* 会话中途改变分辨率时被拒绝，而不是点错位置；
* 二十次启停循环，无遗留进程，基础镜像摘要不变；
* 至少 30 分钟内 1000 个混合动作，检查卡键、泄漏与磁盘增长。

没有硬件加速的 CI 机器可以跑单元测试，以及对可信镜像跑一次 TCG smoke test。这不构成 WHPX 或
隔离属性成立的证据，报告也不得这样呈现。
